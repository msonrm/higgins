# experiments —— 実験と、その結果を焼いたゴールデン

## `ja_hypothesis` —— 日本語の視点反転（2026-08-28）

### 何を確かめたか

英語の DOCTOR は **18 件の置換規則**で視点を反転している（`I→YOU` `MY→YOUR` `ME→YOU` …）。
日本語では **主語を明示しなければ自分の話をしている**と読まれ、しかも DOCTOR は
問い返す機械なので**返しは疑問文 ＝ 省略された主語は二人称**になる。

> つまり ★**主語を省いたまま返せば、置換規則を一つも書かずに視点が反転する**のではないか。

### 結果: 成立した。しかもエンジンは無改造

| 入力 | 出力 | なぜ正しいと言えるか |
|---|---|---|
| 母 が 嫌い です | なぜ **母** が 嫌い な の です か | ★`(私 = あなた)` はスクリプトに書いてあるが**一度も発火していない**（入力に「私」が無いので）。それでも返しは「あなたの母」を指している |
| 私 は 母 が 嫌い です | **あなた** は 母 が 嫌い に なった の は… | 明示されたときだけ置換が効く。★同じ分解パターンの 2 回目なので**テンプレートも巡回している** |
| あなた は 冷たい です | どうして **私** が 冷たい です と 思う の です か | 二人称明示 → 反転 |
| 母 が 好き です | **お母さん** の こと を もっと 話して ください | ★テンプレートは DOCTOR 自身の言葉なので内 → 外 |
| てすと ×5 | 3 回目に **お母さん の こと に 戻り ましょう** | MEMORY は `limit_ % 4 + 1` で **4 回に 1 回** |

★**埋め戻しは「母」、テンプレートは「お母さん」。**
前者は**ユーザーの言葉の引用**なので変換してはいけない（Zenmai の「その文字列は誰のものか」と同じ判別）。

### 入力は**生の日本語**（段階 1 から）

ELIZA の `split_user_input()` は空白区切り前提で、4 言語のうち日本語だけがそれを満たさない。
最初の検証では**手で分かち書き**したが、段階 1 で `tools/wakachi.py` を入れたので
`ja_hypothesis.in` は**生の日本語**になっている（`make test-ja` が wakachi を挟む）。

★**手で切ったときとの差が 2 件出た。両方とも仕様どおりで、むしろ機械のほうが正しい:**

| 差 | 旧（手で切った） | 新（wakachi） | なぜ新しいほうが正しいか |
|---|---|---|---|
| 埋め戻しの粒度 | どうして 私 が **冷たい です** と… | どうして 私 が **冷たいです** と… | ★埋め戻しは**ユーザーの言葉の引用**。元の字面に近いほうが正しい。「冷たい です」は人工的な切り方だった |
| MEMORY の文言 | お母さん の こと に 戻り ましょう | それ は お母さん と 関係 が あります か | ★★**MEMORY のテンプレートは「入力の最後の語のハッシュ」で選ばれる**（`eliza.cpp:2818`）。分かち書きが変われば最後の語が変わる |

> ★Weizenbaum は論文で「規則はランダムに選ばれる」と書いたが、
> **発見されたコードは最後の語のハッシュだった**（Anthony Hay が `doc/Eliza_part_3.md` で追っている）。

### ★日本語で効いてきそうな懸念（予測・未実証）

MEMORY の選択が**最後の語**に依存するということは、★**日本語では文末が「です／ます／でした」に
偏るので、テンプレートの選択も偏りうる**。英語は文末が多様なので分散する。
辞書が育って文末が正しく切り出されるようになるほど、この偏りは強くなるはず。
★**逐語訳では見えない、言語構造そのものに起因する差**なので、日本語 DOCTOR が育ったら測る。

### ★期待値の性質（読む人へ）

`ja_hypothesis.out` は**実測を焼いたもの**。ただし上の表のとおり
**5 件とも「なぜその出力が正しいか」を人間が確認している**。
実装の出力を無検証で期待値にしたわけではない —— それをやると false green になる。

### ★冪等性

`wakachi.py` は**既に分かち書きされた入力を通しても結果を変えない**（空白を区切りとして尊重する）。
確認済み。hechima の文節境界に差し替えるときも、この性質は保つこと。

### この先どう使うか

仮説の証明としての役目は終わった。ここから先は ★**回帰の基準線**:
**hechima の文節境界に差し替えたあと、この挙動が保たれているか**を `make test-ja` で見る。

## `hi_doctor` —— ヒンディー語 DOCTOR のゴールデン（2026-09-03）

`python3 tools/hindi_in.py < hi_doctor.in | build/eliza doctor/hi.txt` を焼いたもの。
★**出口が無い**（日本語の `tsunagi` は「空白を消す」、韓国語の `tsunagi_ko` は
「조사 を実現する」という仕事があったが、ヒンディー語にはどちらも無い）。

### ★入力に**わざと 2 つ仕掛けてある**

1. **合成形の nukta**（U+095B）で書いた行が 1 つ ——「मुझे इसकी ज़रूरत नहीं है।」。
   ★ゲームパッドの合成器が出すのは**分解形**（`deva_nukta` が U+093C を足す）なので、
   入口が寄せていないとこの行だけ見出しに当たらない。
   ★★**画面には同じ字が出る**ので、目で見る検査では絶対に通ってしまう。
2. **danda `।` を空白なしで付けた行**が多数。入口が `.` に写していないと、
   見出しに当たらないうえ**埋め戻しが文をまたぐ**（下記）。

### ★★実測で 2 段深かったところ —— danda は「切る」のではなく「`.` に写す」

はじめは「danda を独立トークンに切る」で済むと思っていた（韓国語で ASCII の句読点を
切っていなかったのと同じ形だと読んだ）。★**それでは足りなかった。**

ELIZA は「キーワードを含む**最初の節**だけを残す」（1966 年論文 page 37(c)）が、
その節の切れ目は **`set_delimeters({",", ".", "BUT"})` でハードコード**されていて、
**スクリプトから増やす入口が無い**。danda を独立トークンにしただけでは節が切れず、
埋め戻しが文をまたいで danda ごと引用に入る（実測「आपके काम मुश्किल है।」）。

→ ★**`.` に写せば、エンジンが既に持っている仕組みにそのまま乗る。**
`?` `!` も `eliza_uppercase` が `.` に潰しているので、扱いが揃うことにもなる。
★画面に出る「打った通り」（`draw_echo`）は生の字なので、**danda は消えない**。

### ★カナリア（この台が生きていることの確認・2026-09-03）

| 壊したもの | 結果 |
|---|---|
| `hindi_in` の danda 写しを外す | ✅ `test-hi-doctor` が赤 / 被覆検査が「`।` 付きの形だけ NONE」を報告 |
| `hindi_in` の nukta 表を空にする | ✅ `test-hi-doctor` が赤（合成形の行が当たらなくなる） |
| **C 版だけ** nukta を落とす | ✅ `make test-native` が「native と CLI のずれ」を捕まえる |
| 別名の飛び先を `(0 माँ 0)` にする | ✅ 被覆検査が**組み込みの英語メッセージ 12 件**を報告 |

★4 つ目は日本語版で 13 件踏んだ形（`ja_alias` と同じ）。**人が打つ前に機械で見つける**。
